1. Who Gives the Tools & Where is problem.json?

Architecture
Q: Is problem.json stored on the external server where the API is hosted?
No! The external API (GPT-Luna) does not store any files. It only receives conversational text and tool descriptions.

All files are created locally by YOUR repo inside your Docker containers:
  • When the harness resets with SEED=0, it generates the mathematical problem instance in memory (weights, capacity, conflicts).
  • The harness sends a reset payload to the Sandbox container via local HTTP (http://sandbox:8000/reset).
  • The Sandbox writes problem.json into its local directory (/workspace/problem.json).
Q: Who gave list_files, read_file, and run_python?
Your harness defined them! In harness/tools.py, you declare OpenAI function definitions:
TOOLS = [ {"name": "list_files", "description": "List every file in the project."}, {"name": "read_file", "description": "Read a text file from the project."}, {"name": "write_file", "description": "Create or overwrite a text file in the project."}, {"name": "run_python", "description": "Run Python code and return its stdout."}, {"name": "finish", "description": "Call this when the task is complete."} ]
When the harness calls GPT-Luna, it passes this list of tools under the tools parameter. GPT-Luna chooses which tool to call, and your local sandbox executes it.

2. How Did GPT-Luna Solve the Problem?

Live Trace Breakdown

In our live test run, GPT-Luna completed the task in 6 steps. Here is its exact strategy:

Step Action Taken Model's Objective
1 & 2 list_files & read_file(problem.json) Discovers the files in the workspace and parses weights, capacity (138), and item conflict pairs.
3 run_python(code=...) The Crucial Step: Rather than calculating manually, GPT-Luna wrote a recursive backtracking depth-first-search solver in Python and executed it inside the sandbox. In 50ms, Python printed the optimal packing: [([13, 12], 130), ([0, 4], 124), ...].
4 write_file(solution.json) Writes the 6 packed boxes into solution.json as requested by the instructions.
5 run_python(code=validator) Runs a second self-check script asserting no item is missing, no box exceeds 138, and no conflicting pairs share a box.
6 finish() Calls finish tool. Harness invokes the hidden verifier → 100% score (1.0).
Key Insight: When an RL environment provides run_python (arbitrary code execution), modern reasoning LLMs will use Python to bypass the reasoning bottleneck. This is why it scored 100% easily!

3. Phase 2: Farm/Economy Without Over-Complication

Rules & Optimal Solvers
The Hackathon Golden Rule:
According to the hackathon specification (Section 04), every single task must have an exact Oracle reference solution that scores ≥ 0.95 in under 2 minutes.
If the game is too chaotic or computationally intractable, you cannot write an oracle that guarantees full marks for every random seed.
The Clean Design: Box Packing → Farm Storage & Shipment Simulation
Instead of building an open-world RPG, map the mathematical problem directly into farm/economy semantics:
  • Items → Harvested Goods / Crops (e.g. Wheat, Apples, Melons) with harvest yields (weights).
  • Boxes → Transport Trucks / Grain Silos with maximum cargo capacity.
  • Conflicts → Agricultural Contamination Constraints (e.g., ethylene-emitting apples spoil nearby vegetables, or flammable chemical fertilizers cannot travel in the same truck as grain).
  • Multi-Step Game Turns → Instead of writing raw python in one shot, the agent plays across Days / Turns:
    • Turn 1: inspect_inventory (sees today's harvest & cargo orders).
    • Turn 2: load_truck(truck_id, item_id).
    • Turn 3: dispatch_truck(truck_id).
    • Turn 4: advance_day().
Why this is guaranteed to work: Because under the hood, the underlying state space remains a constrained bin-packing optimization. Your existing branch-and-bound solver still computes the exact optimal solution in < 25ms, giving you a 100% reliable Oracle Baseline for every seed, while providing judges with an engaging Games & World Simulation!
